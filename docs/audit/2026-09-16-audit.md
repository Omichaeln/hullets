# Audit — 16 September 2026

A focused adversarial pass over this tree, concentrating on the design-level questions that recur in
receipt-promotion systems regardless of how they are implemented, plus what fell out of driving the
console in a real browser.

Every finding below was **reproduced** — driven to a failure against this code, not inferred from
reading it. Each one is pinned by a case in `tests/integration/audit-findings.test.ts` or
`tests/unit/console-routing.test.ts`, written so that it records today's behaviour and will turn red
when the behaviour changes. Where a case asserts the defect (rather than the fix), the comment says
what to flip when it is closed.

Suite after this work: **114 tests**, `npm run typecheck` and `npm run lint` clean.

## Fixed in this pass

### `console-1` — first sign-in rendered a permanently blank console · **blocker**

Every staff member signs in for the first time with a temporary password. `Routes()` handled that by
calling `navigate()` **during render** and returning `null`.

`navigate()` dispatches `tt:navigate` synchronously, and on the first render `usePath`'s
`addEventListener` effect has not run yet — so the event reached no listener, the URL changed, the
component returned `null`, and nothing ever re-rendered. A blank page, on the one path every new
user takes. The API was healthy and every procedure returned correctly throughout, which is why no
existing test saw it; it only looked fine when `/account` was opened directly, because then the
guard never fired.

Fixed by moving the redirect into an effect and rendering the account page immediately, so there is
no blank frame even for one paint. A second, subtler bug surfaced while fixing it: keying the guard
on `path !== "/account"` makes it go false the instant the redirect lands, so a promotion user fell
straight through to the desk and every query failed with `PASSWORD_CHANGE_REQUIRED`. The gate is now
keyed on the flag and outranks console selection.

Verified in a browser, and pinned by `tests/unit/console-routing.test.ts`, which was shown to fail
against the original code.

## Open findings

### `receipts-1` — one purchase can earn two entries, if one rule is turned off · **major, conditional**

The canonical purchase identity is `receiptKey(selectedOutletId, date, receiptNo)`, and
`selectedOutletId` is the outlet the participant **picked from a menu**, not one read off the
receipt. The same till slip, photographed twice and submitted against two branches, therefore
produces two different identities and nothing in the ledger collides.

**It is not exploitable on a default campaign**, and that deserves saying plainly. A separate rule,
`outlet_match`, compares the printed merchant against the selected branch and returns `unknown`,
which the precedence turns into REVIEW. A human sees it. `outletMatch.required` defaults to `true`.
This is a materially better position than the same design in a sibling implementation, where the
double credit was fully automatic.

What the finding pins is that the guarantee is carried by **that rule alone**. Neither duplicate
defence reaches it: exact-bytes matching is defeated by photographing the slip a second time, and
the perceptual (ahash/dhash) matches are recorded as `duplicate_candidates` but never change a
disposition — the code itself calls them a "search signal only". So a campaign configured with
`outletMatch.required: false` — a plausible operational choice where merchant headers scan badly —
silently credits one purchase twice, with no review, no duplicate and nothing in the record to find
later. The test demonstrates both halves: held for review under the default, two active entries with
the rule off.

Two candidate fixes, either of which removes the single point of failure: key the canonical identity
on the merchant **read off the receipt** rather than the one selected, or let a strong perceptual
match block rather than merely annotate. The first is the more complete.

### `audit-1` — attribution can be rewritten in place and the chain still verifies · **major**

Attribution is inside the signed body: `actorType` and `actorId` are both in the canonical JSON the
entry hash covers. That is better than it first appears and is the right design.

But `verify()` only recomputes `sha256(prev + body)` and compares it to the stored entry hash. It
never checks that the **columns** agree with the body it just hashed — and every reader uses the
columns: `audit.list()`, the console, and anything filtering by `actorId`. Rewriting `actor_id` in
place therefore changes who every consumer believes approved a draw, while the integrity check stays
green.

The evidence survives in the body, so this is recoverable rather than fatal — but separation of
duties on draws is only provable by someone who knows to parse the bodies, not by the system's own
verifier or by anything it displays.

The fix is small and needs no schema change: in `verify()`, parse each row's `body` and compare
`actorType` / `actorId` / `action` / `targetType` / `targetId` / `reason` against the columns,
reporting a mismatch the same way a broken hash is reported.

### `ops-1` — the sample-data guard keys on the database's stamp, not the deployment's · **moderate**

The environment is recorded in `schema_meta` on first migration and the **database** value governs
the configuration one. That is the right call, and it closes the defect it was written for: a
forgotten `ENVIRONMENT` variable cannot make a production deployment seed itself, and the config
default is `local` rather than anything production-adjacent. Two further guards are genuinely strict
and keyed on the **config** value, so they fire whatever the database says — production refuses a
simulated extractor and a simulated transport at config validation, before any of this is reached.
I expected that to be bypassable and it is not.

The residual gap is the other direction. `tools/seed.ts` refuses only when
`app.environment === "production"`, and `app.environment` is the database's stamp. A database stamped
`staging` — a staging backup restored into production, or a staging database promoted — leaves the
sample-data guard permissive under production configuration. `schema_meta` is written
`onConflictDoNothing`, so the stamp is permanent and no later migration corrects it. The mismatch is
logged as a warning and the boot continues.

Fix: take the **stricter** of the configured and recorded environments wherever a guard keys on it,
or refuse to boot on a mismatch rather than warning. The warning already exists and names both
values, so the information is there.

### `ops-2` — `npm test` dirties the working tree · **minor**

The OCR suite rewrites `docs/testing/evidence/ocr-pipeline-results.json` on every run with a fresh
timestamp and per-fixture millisecond timings. The content is otherwise identical — same 35
fixtures, same 35 agreements — so every contributor gets a spurious modified file after running the
tests, and a real change to that evidence is hidden in the noise. Either write it only under an
explicit flag, or drop the timing fields that cannot be stable.

## Checked and found sound

Worth recording, because a finding that does not land is as useful as one that does:

- **Environment fallback.** `ENVIRONMENT` defaults to `local`, not to a production-adjacent value,
  and the database stamp governs. The class of defect where a forgotten variable seeds sample data
  into production is closed.
- **Production transport and extractor guards.** Both are enforced at config validation on the
  configured value, so a weaker database stamp cannot relax them.
- **Audit body coverage.** Actor attribution is inside the hashed body, not alongside it.
- **`platform_admin` cannot read the overview.** This looks like a misconfiguration and is not: the
  policy header states that platform_admin is technical and never implies review, draw, approval or
  prize authority, and the permission table matches the stated intent.
- **Separation of duties on draws** is enforced (officer ≠ approver) and the draw engine is
  deterministic and independently verifiable.

## Method

Fixtures and the simulated extractor, against a throwaway PostgreSQL database per suite with real
constraints and real transactions. Console behaviour was driven in Chromium against the real API,
which is the only reason `console-1` was found at all — it is invisible to every API-level test,
because nothing was failing on the server.

The console guards in `tests/unit/console-routing.test.ts` are **source assertions**, not
behavioural tests: nothing there renders React. They are labelled as such in the file. They pin the
specific anti-pattern so it cannot come back silently; they cannot prove a screen renders.
